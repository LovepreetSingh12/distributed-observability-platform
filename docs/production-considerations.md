# Production considerations and known limits

This is a functional local platform and a starting point for further engineering, not a production certification.

- Compose is localhost-only and single-node. Kafka replication factor 1, min ISR and Mongo single-member replica set are for development. Use multiple brokers/replica members, tested backups, authenticated TLS connections, network controls and explicit resource sizing in production. Do not expose Mongo, Kafka or the unauthenticated sample application publicly.
- Disable `DEMO_SEED`; provision tenants, users and memberships operationally. This version has no signup, invitation, password recovery, membership administration UI, SSO or MFA. BCrypt protects passwords, and 256-bit random API/token secrets use SHA-256 hashes. Production needs login abuse protection, audit records and a credential rotation process. Current login has no rate limiting. API keys are revocable but do not expire automatically.
- User tokens expire after 8 hours, are revocable by logout, and memberships are checked on each request. The browser uses sessionStorage; an XSS vulnerability can expose its bearer token. Static frontend has a CSP and renders payload JSON as text. Use HTTPS at the edge. Service logging does not intentionally record credentials/bodies; keep HTTP/security debug logging disabled, and ensure applications do not log secrets themselves.
- Ingestion rate limiting is per process, per tenant/application, using fixed windows. Bursts can occur at window boundaries and additional replicas multiply capacity. This is not a distributed/global quota. Sustained abuse needs an edge policy or distributed limiter in a future iteration.
- The SDK's in-memory buffering loses data on crashes and under configured drop conditions. It has no disk spool. JSON conversion still costs CPU on the logging thread. Excessively large caller-created payloads consume memory before ingestion rejects them. Neither the SDK nor the platform promises durable/exactly-once delivery end to end.
- Current ingress publishes and awaits individual event acknowledgments sequentially. Large batches with repeated dependency timeouts can outlast the SDK request timeout and produce ambiguous outcomes/replays. Keep healthy batches small; optimize acknowledgment pipelining before high-throughput deployment. Event IDs make replay safe in storage.
- Event retention defaults to 14 days from receivedAt. Kafka ingestion topic defaults to 7 days and DLQ 14 days. Changing `.env` does not alter an already-created Kafka topic's retention; apply `kafka-configs.sh --alter` explicitly. Size Kafka retention for maximum expected outages/replay time.
- Mongo TTL cleanup is asynchronous; expired records may remain visible until the background monitor deletes them. Expiry is a retention mechanism, not an exact deletion SLA. Replayed expired records retain original expiry. No client can extend retention in the envelope.
- Published schema cache is bounded to 512 entries per ingestion process. Published data must remain immutable even for direct database operators. Missing schemas are not cached. Validation is bounded by JSON size/depth, but pathological schema regex/combinator complexity still needs operational review; administrators are trusted schema authors. Only internal schema references are supported.
- Mongo is suitable for moderate event search and bounded analytics, not a substitute for a dedicated high-volume column store/search engine. Payload filters scan unless intentionally indexed by an operator. The application never indexes arbitrary payload fields automatically. There is no full-text search, percentile metric, joins, arbitrary pipeline, or cross-tenant analytics endpoint.
- Query range 30 days, page size 200, 50 groups, 500 time buckets and three-second DB timeouts are deliberate limits. Empty time buckets are not filled. Cursor pagination is stable by timestamp/UUID but is not a snapshot across late arrivals or TTL deletions.
- Dashboard queries run separately; panels may reflect slightly different ingestion progress. Refresh uses polling, and the mobile editor uses horizontal scrolling for its 12-column grid. Query JSON editing is intentionally structured but basic; there is no visual query builder for every operator.
- Integration tests use real MongoDB and mocked failure boundaries for ack/DLQ tests; the full smoke uses real Kafka. They do not prove behavior under every broker failover, host crash, disk-full scenario or long outage. Add sustained load, fault injection, multi-replica and upgrade testing before production.
- Container tags and library versions are pinned; pin image digests and maintain a patch/update process before deployment. Java services expose health but there is no external monitoring, alerting, billing, Redis, Elasticsearch or Kubernetes in this scope.
